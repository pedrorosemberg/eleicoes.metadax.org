# ISO 27001 / ISO 27002 — o que se aplica a este projeto e o que não se aplica

Documento criado a pedido do mantenedor (26/08/2026), que pediu para "integrar as boas práticas
da ISO 27001 e ISO 27002" ao projeto. Antes do mapeamento em si, uma distinção que precisa ficar
clara — inclusive porque este projeto tem como princípio central nunca fabricar ou inflar uma
afirmação (ver `docs/DATA_SOURCES.md` §10 sobre dado; o mesmo princípio vale para afirmação de
conformidade):

## O que a ISO 27001 realmente é (e por que não se aplica a um repositório isolado)

A **ISO/IEC 27001** é uma norma de **sistema de gestão** (ISMS — Information Security Management
System). Ela certifica uma **organização**, não um software: exige política de segurança da
informação assinada pela direção, análise de risco formal com registro (risk register), comitê ou
responsável de segurança, plano de tratamento de risco, auditoria interna periódica, reunião de
análise crítica pela direção (management review), e — para a certificação valer — uma auditoria
externa por um organismo credenciado. Nada disso é algo que um repositório de código, sozinho,
pode "ter" ou "não ter". A entidade que poderia buscar certificação ISO 27001 aqui seria a
METADAX/o Instituto METADAX de Inovação como organização, não o projeto `eleicoes.metadax.org`
isoladamente — e isso está fora do escopo do que uma sessão de desenvolvimento de software pode
implementar ou declarar.

**Por isso este documento não declara "conformidade com a ISO 27001"** — seria uma afirmação que
este projeto não tem como sustentar nem verificar, o equivalente a fabricar um dado. O que ele faz
em vez disso: mapear os controles técnicos da ISO 27002 (o catálogo de controles que dá suporte a
um ISMS) que **são aplicáveis a nível de projeto/software**, e mostrar exatamente onde cada um já
está implementado neste repositório — sempre apontando para o arquivo/mecanismo real, nunca uma
afirmação solta.

## O que a ISO 27002 é, e como este documento usa ela

A **ISO/IEC 27002** é o catálogo de controles de referência citado pela ISO 27001 (Anexo A) — uma
lista de práticas técnicas e organizacionais (controle de acesso, criptografia, segurança em
desenvolvimento, gestão de fornecedores, resposta a incidente, etc.), cada uma com um identificador
(ex.: `8.25`). Diferente da 27001, vários desses controles individuais **fazem sentido e são
verificáveis** num projeto de software isolado — é isso que a tabela abaixo mapeia.

## O que fica fora de escopo, e por quê

- **Controles físicos (Anexo A, seção 7)** — segurança de datacenter, controle de acesso físico:
  responsabilidade da Vercel/GitHub como provedores de infraestrutura, fora do controle deste
  projeto (mesmo racional já aplicado a "infraestrutura de terceiro" em `docs/DATA_SOURCES.md`).
- **Recursos humanos (Anexo A, seção 6)** — triagem de contratação, treinamento formal de
  conscientização: não se aplica a um projeto de código aberto mantido por uma pessoa.
- **Continuidade de negócio formal** — este projeto não tem SLA nem obrigação contratual de
  disponibilidade (`SECURITY.md`, `/participe`); resiliência real (cache, degradação graciosa por
  fonte) está implementada, mas não como plano de continuidade formal com RTO/RPO definidos.
